# OpenClicky current capability and delivery plan

Updated 12 October 2026. This document separates implementation, automated proof, native Windows acceptance, and Ahmad's physical acceptance. Earlier milestone evidence remains below; it does not describe the whole current product.

The requested video review is complete: [Hey Clicky video review](heyclicky-video-review-2026-10-12.md). It covers all 13 supplied videos (48:32 total) and records timeline samples, product implications, and proof limits. OpenClicky 0.6 now has one companion across persistent local voice, automatic dictation with a preserved review fallback, tasks/receipts, clipboard, bounded learned memory, seven drawing primitives, guided walkthroughs, a bundled OpenWork runtime and an actual CopilotKit v2 workspace renderer. Broader physical reliability, optional dictation rewrite, named companions, routines and live connectors remain unfinished.

## Evidence levels

- **Built:** the production code path exists and has relevant automated or focused checks.
- **Native accepted:** the behavior was observed in the running Windows app and, for desktop actions, in the actual destination control.
- **User physical accepted:** Ahmad personally confirmed the hardware or interaction result. This is narrower than general reliability.
- **Planned:** research or design exists, but the production behavior does not.

One capability can have more than one level. A passing build or test does not imply native or user acceptance.

## What the video review changed

The review converted the supplied product demonstrations into a safe implementation order:

1. Dictation must preserve the raw transcript and editable draft even while automatic-on-pause insertion serves the fast path; reviewed insertion remains an explicit fallback.
2. Selected regions must remain visible as scoped context and become invalid when the application changes.
3. Drawing needs more shapes, while walkthroughs need explicit state, result observation, and Next/Back/Stop controls.
4. Phase one keeps one companion coherent across surfaces; phase two may add named companions with bounded roles and explicit approval.
5. Connectors should expose identity and scopes and begin read-only; routines should follow companion acceptance.

The current product already implements pieces of that direction—region selection, persistent voice, review-first rich actions, task receipts, and the dock—but the remaining rows above are still real work. The independent DaVinci Resolve recording shows a person manually editing video; it is reference material, not evidence of autonomous video editing.

1. **Initial visual set accepted:** real chart, branched diagram, calculator and cube generation passed. Native controls, saved edits and retention of prior visuals survived normal app restart. Broader generated payloads remain bounded by the supported renderer contract.

Record matching archive hashes and zero unresolved licenses; physical latency remains unaccepted.
3. **Accept automatic dictation physically:** verify two ordered pause-separated insertions plus the preserved edited fallback, then test broader accuracy/repeated sessions before optional rewrite work.
4. **Broaden spatial and renderer acceptance:** verify a real model-produced curve, mixed DPI, Escape, renderer reload/failure behavior, diagram values and bounded 3D output.
5. **Close voice hardware checks:** physical tray/shortcut, Stop/Pause/Resume/change-task, AEC interruption, noise, disconnect and long-session behavior.
6. **Add routines only after the one-companion boundaries are accepted:** visible schedules, Run now, Pause, approval-aware waiting, safe catch-up, failure receipts and history.
7. **Connect one read-only account:** show identity/scopes, revocation, sources and a verified read receipt before any write capability.
8. **Harden distribution:** sign packages and complete clean-machine upgrade, accessibility and mixed-DPI acceptance.

## Safety and proof boundaries

Confirm each remains the default. Auto and Full access require a visible warning, and a running task's access snapshot must not silently widen. Auto relies on conservative rationale/argument matching and can miss sensitive actions. Full access can change visible data without individual approvals. Title checks, cancellation, and changed-window/revision checks reduce accidental actions but are not security boundaries.

Keep provider secrets out of source, settings JSON, logs, and Chat. Do not automate sign-in, credential entry, or Windows security changes. Explain which screen pixels and audio leave the machine. Verify desktop actions in their destination controls and retain receipts; a running process, planner response, or passing unit test alone does not prove the user-visible result.
